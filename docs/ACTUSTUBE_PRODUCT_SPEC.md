## 1. 製品定義と基本理念

### 1.1 製品概要

ActusTubeは、YouTube投稿者向けのAI分析・改善SaaSである。YouTube Studio等で得られる数値を単に再表示するのではなく、投稿者固有の投稿履歴、動画の成果傾向、強み・弱みを分析し、次回の制作行動へ変換することを目的とする。

中核価値は「数値を見る」から「次に何をするか決め、実行し、結果を振り返る」への移行である。AIはコンサルタント役を担うが、根拠を示さない断定や過度な期待を避ける。

### 1.2 解決する課題

- 分析画面に数値はあっても、投稿者が次の動画で何を変えるべきか判断しにくい。

- チャンネルごとに成功要因が異なり、一般論だけでは実行可能な改善策になりにくい。

- 一度分析して終わりになり、改善内容・実行状況・結果が継続的に蓄積されない。

- AIの助言は根拠や不確実性が曖昧だと信頼されにくい。

- 分析本数・AI利用量が無制限だと、サービス提供原価が料金を上回る危険がある。

### 1.3 製品原則

| 原則 | 仕様上の要求 |
| --- | --- |
| 根拠性 | 提案は対象動画・統計・比較傾向など、確認可能な材料に結び付ける。 |
| 具体性 | 投稿主が次の制作でそのまま実行できる粒度の行動にする。 |
| 慎重さ | 因果関係を断定せず、不確実性、データ不足、外部要因を明示する。 |
| 継続性 | 分析→改善項目→実行→結果メモ→次回分析のループを支える。 |
| 快適性 | 主要導線、待機状態、エラー、レスポンシブ表示を明確にする。 |
| 採算性 | どのプランでも変動原価が収益を超えない利用上限を設ける。 |
| 安全性 | OAuthトークン、Cookie、APIキー、個人情報を画面・ログ・文書へ露出しない。 |

## 2. 対象ユーザーと利用シナリオ

### 2.1 主要ユーザー

| ユーザー像 | ニーズ | 主要機能 |
| --- | --- | --- |
| 個人投稿者 | 少ない時間で次回改善点を知りたい | 自動集計、強み・弱み、次回提案 |
| 成長期チャンネル | 再現性のある企画・構成を見つけたい | ランキング、低再生抽出、週次改善 |
| 本業クリエイター | 投稿履歴全体を横断し、継続的な助言が欲しい | Pro構想、履歴、トレンド、予測 |
| 小規模運営チーム | 改善内容と結果を共有したい | 改善項目、状態、結果メモ。共有機能は将来要件 |

### 2.2 標準利用シナリオ

1. Googleアカウントでログインし、YouTube読み取り権限を許可する。

1. 所有・管理する対象チャンネルを取得または選択する。

1. 通常動画とShortsを取得し、対象本数と利用枠を確認する。

1. 統計、月別推移、分布、上位・低成果動画を確認する。

1. AI提案を実行し、強み・弱み・改善点・次回案を読む。

1. 今週の改善項目を1件作成し、plannedからcompletedまたはskippedへ更新する。

1. 結果メモを残し、履歴を次回の分析・判断に利用する。

### 2.3 対象外・注意

- YouTubeの成果や収益を保証するサービスではない。

- 動画を自動投稿・削除・編集する権限は現行MVPの対象外。

- YouTube Analytics APIによる詳細収益・視聴者維持率等は現時点で未実装。

- 人間の専門家による法務・税務・広告表示審査を代替しない。

- 複数メンバーの権限管理、代理店向け一括管理は将来要件。

## 4. システム構成

### 4.1 技術スタック

| 層 | 採用技術 | 役割・基準 |
| --- | --- | --- |
| フロント／サーバー | Next.js 15.5.21 / React 19.0.0 | App Routerベースの画面・サーバーAPI |
| 認証 | Auth.js | Google OAuth、セッション、アクセストークン更新 |
| DB | Neon PostgreSQL / Drizzle ORM | ユーザー、利用枠、分析履歴、改善項目 |
| AI | OpenAI API | チャンネル固有の分析・改善提案 |
| 動画データ | YouTube Data API | チャンネル・動画・公開統計の取得 |
| ホスティング | Vercel / Node.js 24.x | Preview・Productionの自動デプロイ |
| テスト | Vitest 4.1.10 / Testing Library / jsdom | ロジック・API・React実行経路の検証 |
| 画像変換 | sharp 0.35.3 / libvips package 1.3.2 | サーバー側画像処理。単一版を維持 |

### 4.2 論理アーキテクチャ

1. ブラウザがNext.js画面へアクセスし、Auth.jsセッションを取得する。

1. 認証済みAPIのみがGoogle／YouTubeのアクセストークンをサーバー側で使用する。

1. YouTube Data APIからチャンネル・動画・公開統計を取得し、画面用データへ整形する。

1. 分析処理が集計値・動画特徴・ランキングを作成する。

1. AI提案APIが必要最小限の分析結果をOpenAI APIへ渡し、構造化された助言を返す。

1. 成功時のみ、利用枠確定と履歴保存をDBトランザクション相当の原子的処理で行う。

1. 改善項目と状態・結果メモを保存し、履歴として再表示する。

### 4.3 外部サービス境界

| サービス | 送信／取得データ | 障害時の要求 |
| --- | --- | --- |
| Google OAuth | 認可コード、セッションに必要な識別情報 | 認証エラーを一般画面へ戻し、秘密情報を表示しない |
| YouTube Data API | チャンネルID、動画ID、公開統計 | タイムアウト・権限不足・quota不足を区別可能にする |
| OpenAI API | 分析に必要な統計・要約情報 | 失敗時に成功履歴を保存せず、再送信を抑止する |
| Neon | 認証・利用枠・履歴・改善項目 | DB不整合時は処理を成功扱いにしない |
| Vercel | アプリ実行、ログ、デプロイ | 自動デプロイ失敗時は手動操作せず原因確認で停止 |

## 5. 認証・YouTube連携

### 5.1 Googleログイン

| ID | 要求 | 受入条件 |
| --- | --- | --- |
| AUTH-01 | 未認証ユーザーにGoogleログイン導線を表示する。 | ログイン開始が1回の操作で行える。 |
| AUTH-02 | YouTube読取権限 youtube.readonly を要求する。 | 投稿・削除権限は要求しない。 |
| AUTH-03 | 認証済みAPIをセッションで保護する。 | 未認証アクセスは401となる。 |
| AUTH-04 | ログアウト後に認証済みデータへアクセスできない。 | セッションが無効化され、画面が未認証状態へ戻る。 |
| AUTH-05 | OAuthトークンをクライアントへ露出しない。 | HTML、JSON、Console、URLにトークンがない。 |

### 5.2 アクセストークン更新

- 有効期限切れ前後にrefresh tokenを使用してサーバー側で更新する。

- 同一ユーザーの同時更新をsingle-flightでまとめ、重複refreshを避ける。

- invalid_grantは再ログインが必要な認証失効として扱う。

- Google側5xx、通信タイムアウト、一時障害は秘密情報を隠した一般エラーに変換する。

- refresh tokenが取得できない場合、無限再試行せず再認証を案内する。

### 5.3 チャンネル取得

認証ユーザー自身がアクセス可能なチャンネルを取得する論理機能をYT-CH-01とする。確認できているRouteは GET /api/youtube/my-channels である。過去の401ログは公開前の認証問題に関する履歴であり、2026-07-22の現行Production障害を示すものではない。

| 状態 | 表示・動作 |
| --- | --- |
| 未認証 | ログインを案内。チャンネル取得APIは401。 |
| 取得中 | 読込状態を表示し、同一操作を無効化。 |
| 成功・1件 | 対象チャンネルを選択済みとして表示可能。 |
| 成功・複数 | ユーザーが分析対象を明示選択。 |
| 0件 | YouTubeチャンネルが見つからない旨と確認方法を表示。 |
| 権限不足 | 再認証または権限確認を案内。 |

## 6. 動画取得・分析

### 6.1 動画分類・取得

| ID | 要求 | 備考 |
| --- | --- | --- |
| VID-01 | 通常動画とShortsを分けて取得・表示する。 | 分類規則は実コードを正本とし、境界条件テストを維持する。 |
| VID-02 | 新しい動画からプラン上限までを分析対象にする。 | Freeは各10本。候補プールは各50本。 |
| VID-03 | 同じ動画を重複集計しない。 | 動画IDを論理一意キーとして扱う。 |
| VID-04 | 取得できない非公開・削除動画を成功データとして捏造しない。 | 欠損を許容し、件数差を説明可能にする。 |
| VID-05 | API quotaとアプリ利用枠を別々に管理する。 | 外部API quota不足をユーザー利用超過と混同しない。 |

### 6.2 集計指標

| 指標 | 定義・目的 | 表示上の注意 |
| --- | --- | --- |
| 合計再生数 | 対象動画の再生数合計 | 取得対象本数・期間を併記する。 |
| 平均再生数 | 再生数合計÷対象本数 | 極端なヒット動画の影響を受ける。 |
| 中央値再生数 | 再生数を並べた中央値 | 典型的な成果把握に使用。 |
| 投稿頻度 | 対象期間の投稿日間隔または期間当たり投稿数 | 期間が短い場合は断定を避ける。 |
| 月別推移 | 公開月単位の本数・再生傾向 | 直近月が未完了なら注記する。 |
| 再生数分布 | 動画群を再生規模別に把握 | 通常とShortsを混在比較しない。 |
| ランキング | 対象範囲内の上位動画 | 全期間順位ではなく対象範囲順位である。 |
| 低再生抽出 | 対象群の相対的な低成果動画 | 失敗と断定せず、改善材料として扱う。 |

### 6.3 分析実行

1. 認証とチャンネル選択を確認する。

1. プラン上限と現在利用量を確認し、実行可否を判定する。

1. 動画データを取得・整形し、通常動画とShortsを分離する。

1. 集計、月別推移、分布、ランキング、低成果抽出を生成する。

1. すべての必須処理が成功した場合のみanalysis_runsへ保存する。

1. 失敗した処理を成功履歴として保存せず、利用者に再実行可否を説明する。

### 6.4 分析結果の解釈ルール

- 相関を因果として表現しない。例：特定の長さと再生数の関係だけで成功要因と断定しない。

- サンプル数が少ない場合は「傾向」と表現し、信頼度を下げる。

- Shortsと通常動画は視聴行動が異なるため、原則別評価とする。

- 公開時期、話題性、外部流入、サムネイル変更等の未取得要因があることを明示する。

- 分析対象本数・期間・欠損を画面または提案根拠で確認できるようにする。

## 7. AIコンサルティング

### 7.1 目的と入力

AIは、一般的なYouTube論ではなく、対象チャンネルの実データに結び付いた改善案を生成する。入力は必要最小限にし、OAuthトークン、Cookie、APIキー等を含めない。

| 入力カテゴリ | 内容 | 注意 |
| --- | --- | --- |
| チャンネル概要 | チャンネル名、説明、公開統計等 | 個人情報の過剰送信を避ける。 |
| 動画群 | タイトル、公開日、再生数、種別等 | 上限本数と対象期間を固定する。 |
| 集計 | 平均、中央値、投稿頻度、分布、上位・低成果 | 算出済み値を優先し、AIに再計算を委ねすぎない。 |
| 履歴 | 過去分析、改善項目、状態、結果メモ | 必要な範囲だけを渡す。 |
| ユーザー指示 | 今回重視するテーマ等 | プロンプト注入や機密入力を考慮する。 |

### 7.2 出力構造

| 項目 | 必須内容 | 品質基準 | 状態 |
| --- | --- | --- | --- |
| 強み | 再現可能な長所 | 根拠となる動画・数値傾向を示す | 公開済み |
| 弱み | 改善余地 | 人格批判を避け、観測事実と推測を分ける | 公開済み |
| 改善点 | 優先順位付きの具体行動 | 次回制作で実行できる粒度 | 公開済み |
| 次回提案 | 動画ネタ、構成、制作方法 | チャンネル特性と過去傾向に結び付ける | 公開済み |
| 期待効果 | 改善によって期待する変化 | 保証表現を避け、測定指標を示す | 未実装 |
| 根拠 | 提案とデータの対応 | 対象範囲・不確実性を明示 | 設計確定 |

### 7.3 AI文章ポリシー

- 『必ず伸びる』『確実に収益が増える』などの保証表現を禁止する。

- 提案ごとに、観測事実、解釈、推奨行動を区別する。

- データ不足時は不足を明示し、無理に結論を作らない。

- 投稿者が即座に行動できるよう、対象、変更点、期限または次回動画、確認指標を示す。

- 否定的な結果も尊重ある表現にし、改善可能な行動へ変換する。

- YouTubeポリシー違反、誤認誘導、危険行為を勧めない。

### 7.4 保存・利用枠

AI提案は成功した場合のみ履歴へ保存する。利用枠の確定と履歴保存はDB関数で原子的に行い、片方だけ成功する状態を避ける。外部AI呼出しが失敗した場合の実原価は発生し得るため、課金・原価管理では『ユーザー枠確定』と『実コスト計測』を分ける。

## 8. 週次改善サイクル

### 8.1 目的

分析結果を読むだけで終わらせず、1週間単位の改善行動へ変換し、実行結果を次の判断材料にする。MVPでは『今週の改善サイクル』と履歴一覧を提供する。

### 8.2 改善項目

| フィールド | 内容 | 必須／制約 |
| --- | --- | --- |
| 改善内容 | ユーザーが実行する具体的な行動 | 必須。空文字不可。 |
| 状態 | planned / completed / skipped | 既定はplanned。許可値以外を拒否。 |
| 結果メモ | 実行後の結果、気付き、次回への反省 | 任意。保存後に再表示。 |
| 関連分析 | どの分析結果から作成したか | 論理関連。正確なFKは要コード確認。 |
| 作成・更新日時 | 履歴順序と監査の基礎 | サーバー時刻基準。 |

### 8.3 業務ルール

| ID | ルール | 結果 |
| --- | --- | --- |
| ACT-01 | 進行中の改善項目は同時に1件まで。 | 重複作成はDB一意制約で防止し、APIは409へ変換。 |
| ACT-02 | 作成・更新中は操作ボタンをdisabledにする。 | 連続クリックによる二重送信を防ぐ。 |
| ACT-03 | 作成・更新API成功後に先頭ページを再読込する。 | 最新履歴へ置換する。 |
| ACT-04 | 保存成功後の再読込失敗は部分成功として扱う。 | 成功通知で上書きせず、ページ再読込を案内するerrorを表示。 |
| ACT-05 | 履歴は10件単位のカーソルページネーション。 | 重複・欠落を避けて追加読込。 |
| ACT-06 | 更新後も状態・結果メモを永続化する。 | 再表示時に保存値が保持される。 |

### 8.4 通知仕様

| ケース | 最終通知 | アクセシビリティ |
| --- | --- | --- |
| 作成成功＋再読込成功 | 成功通知 | role=status / aria-live=polite |
| 更新成功＋再読込成功 | 成功通知 | role=status / aria-live=polite |
| 作成成功＋再読込失敗 | 作成済みの可能性とページ再読込を案内するerror | role=alert / aria-live=assertive |
| 更新成功＋再読込失敗 | 保存済みの可能性とページ再読込を案内するerror | role=alert / aria-live=assertive |
| API失敗 | 成功通知を消し、errorのみ表示 | role=alert / aria-live=assertive |

- Content-TypeとJSON schemaを検証し、不正入力は4xxで拒否する。

- 外部サービスの生エラー、トークン、接続文字列、stack traceをレスポンスへ含めない。

- 重複作成は409など、ユーザーが再送信判断できる状態へ変換する。

## 13. エラー・非同期状態

### 13.1 共通状態モデル

| 状態 | 画面挙動 | 禁止事項 |
| --- | --- | --- |
| idle | 操作可能。過去通知は必要に応じて保持または消去。 | 未入力で実行させない。 |
| pending | 進行表示、関連ボタンdisabled。 | 二重送信、連続クリック、別成功通知の表示。 |
| success | 最新成功結果とstatus通知を表示。 | 古いerrorとの混在。 |
| partial success | 保存済み可能性と確認方法をalert表示。 | 成功通知でerrorを上書き。 |
| error | 原因の種別とユーザーが取れる行動をalert表示。 | 秘密情報、生stack trace、無限再試行。 |
| empty | データがない理由と次の操作を案内。 | ゼロ件を障害または成功データと誤認。 |
| limit reached | プラン上限と次回可能時期または上位プランを案内。 | 実行後にだけ上限を伝える。 |

### 13.2 unmount・競合

- コンポーネントunmount後の不要なstate更新を避ける。

- 古いリクエストの応答が新しい画面状態を上書きしないよう、request識別または取消を検討する。

- 作成・更新完了後の再読込結果で通知を上書きする際、保存結果と読込結果を別の成否として扱う。

- fetch reject、非2xx、不正JSON、schema不整合を別経路としてテストする。

- disabled解除はresolve/rejectの両経路で保証する。
